# Web upstream TLS verification — 5.2.14

During the independent CMT-003B source review, all three Web nginx HTTPS proxy locations (`/api/`, `/tts/`, `/socket.io/`) explicitly set `proxy_ssl_verify off`. This encrypts traffic without authenticating the upstream certificate. The patch installs the CA bundle in the existing nginx image, enables certificate verification at server scope with depth 3 and an explicit API TLS/SNI hostname, removes the three bypasses, and adds `nginx -t` to the existing container startup, where private WebSocket DNS is available. The private HTTP `/ws/` routing is unchanged; no provider connection/settings or external proxy is created.

Source reference: [nginx proxy SSL directives](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_ssl_verify), including trusted CA file and certificate-name/SNI semantics. No application checks run locally. Existing production autodeploy supplies build/configuration/startup evidence; anonymous browser GET through `/api/admin/uat-fixtures/<synthetic-run-id>` must return API denial rather than a gateway error after deploy. No paid TTS, live Socket.IO session or customer request is exercised. Valid upstream transport does not prove a malicious-certificate negative test or authenticated application acceptance.

This is a separate fix from tenant-configured CRM egress. Browser still uses origin checks without DNS socket pinning; the socket-enforcement/private-sandbox acceptance gap remains open and must not be declared fixed by nginx verification. Current BrowserView sessions are shared by default; a proposed egress broker must first isolate trusted tenant sessions so it cannot route unrelated tabs through a tenant policy. Native Browser networking requires a supported native acceptance channel and a tenant-approved DNS/CRM sandbox; no such runtime/sandbox is evidenced in this invocation.
