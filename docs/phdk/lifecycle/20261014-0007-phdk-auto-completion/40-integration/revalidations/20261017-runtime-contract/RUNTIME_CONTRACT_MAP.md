La reclamación solo registra `claimedAt`; en el código inspeccionado no se encontró expiración, heartbeat, requeue ni liberación al desconectar. Si Browser o la red cae después de la reclamación y antes de que API guarde `browser.command.result`, el poller no vuelve a recibir ese comando. El flujo queda huérfano sin recuperación visible.\n\nEl result endpoint es idempotente para `commandId` ya completado, pero no hay una clave de idempotencia visible que el efecto CRM pueda usar. Reintentar a mano con un comando nuevo podría repetir el efecto. La corrección requiere elegir semántica explícita (lease + entrega al menos una vez con receiver idempotente, o at-most-once y reconciliación/manual recovery), mantener el mismo id de operación y distinguir `claimed`, `running`, `completed` y expirado. No reemitir automáticamente CRM mutations hasta resolver esta política.\n\n### INT-003-02 — DNS/rebinding para allowlists tenant\n\nAPI/Cloud normalizan origen HTTP(S) exacto por tenant; Browser restringe navegación y solicitudes a esos orígenes. Se permiten orígenes privados configurados, según la política aprobada. No se encontró comprobación de IP resuelta/CIDR ni defensa frente a DNS rebinding entre validación y conexión. No presentar el origen allowlist como protección completa para metadata/loopback; resolver/pinear el destino en la capa de red preservando la excepción privada tenant aprobada antes de aceptar CRM privados.\n\n### INT-003-03 — adaptador y sandbox externos\n\nEl proveedor de llamadas, el CRM, el flujo y el host privado los elige cada cliente. No inferir Salesforce, Genesys, CallPicker ni ningún destino por configuración histórica o navegador de cliente. Conformance E2E queda pendiente hasta que un propietario entregue un sandbox/contrato y autorice una prueba sintética.\n\n## Trabajo siguiente\n\n1.
